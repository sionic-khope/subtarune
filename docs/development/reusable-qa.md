# 재사용 QA 실행 가이드

Codex·Claude·Fable 및 다른 에이전트가 공유하는 실행 절차다. 하네스/플러그인 이름과 무관하게 이 저장소의 도구를 사용한다. 검사할 범위는 [회귀 선택표](regression-checks.md), 완료 판단은 [검수 스킬](../../.claude/skills/subtarune-verify/SKILL.md)이 원본이다.

## 먼저 재사용한다

1. `tests/playtest/run.sh --list`로 이름을 찾고 관련 시나리오 **한두 개의 본문**을 읽는다. `rg -n '키워드' tests/playtest tests/unit`로 추가 탐색한다. 존재만 확인하지 말고 어떤 입력·기대값·fixture인지 확인한다.
2. 기존 시나리오가 요구를 검사하면 그대로 실행한다. 새 보스의 규칙은 시나리오에 추가하고, 브라우저/입력/대기/캡처/오류/결과 저장은 [harness.mjs](../../tests/playtest/lib/harness.mjs)를 재사용한다. 일회성 HTML·별도 Playwright 런처를 기본으로 만들지 않는다.
3. 특정 패턴을 고르는 턴/스택/HP 주입과 기대 피해·타이밍·대사는 전투별 코드에 둔다. 공통 helper 안에 보스 이름별 분기를 늘리지 않는다. 두 시나리오에서 실제 중복이 확인되면 가장 작은 helper를 추출한다.
4. 변경된 시나리오의 검사와 영향을 받는 공통 소비자를 실행한다. 모든 보스·모든 캡처를 매번 실행하는 대신 범위를 먼저 선택한다. 명령 목록/인자는 `--help`를 원본으로 삼는다.

## 실행과 동시 작업 보호

```sh
# 캐시와 브라우저가 없어도 도움말/목록부터 확인할 수 있다.
tests/playtest/run.sh --help
tests/playtest/run.sh --list

# 자신의 checkout을 별도 터미널에서 서빙한다. 사용 중인 포트를 확인해 선택한다.
python3 -m http.server 8879 --bind 127.0.0.1 --directory /absolute/path/to/worktree

# 현재 이전을 완료한 두 시나리오: 비기본 URL을 지원한다.
QA_BASE_URL=http://127.0.0.1:8879 \
  QA_ARTIFACT_DIR=/absolute/path/to/evidence \
  tests/playtest/run.sh battle_lose battle_bgm
```

메인에서 다른 에이전트가 작업 중이면 별도 worktree/서버로 검증한다. 서버 URL이 같은 BUILD라고 같은 소스는 아니다. cwd/SHA/미커밋 차이와 서빙 경로를 확인한다. 러너의 소스 비교가 있더라도 일부 파일 비교는 저장소 전체 동일성 증명이 아니다. 다른 작업자의 서버·브라우저·저장 상태를 재기동하거나 초기화하지 않는다.

HEAD에서 만든 worktree에는 메인의 미커밋 변경이 없다. 그 변경을 검수하는 요청이면 소유자와 대상 diff를 확인하고 재현 가능한 패치를 격리 트리에 적용한 뒤 검사한다. 테스트 도구 자체만 만드는 요청에는 관련 없는 게임 변경을 가져오지 않는다. `summary.json`의 로컬 SHA와 `requestedBaseUrl`은 각각의 기록이지 서버 전체 소스 동일성 보장이 아니다.

`PW_DIR`는 기존 `playwright-core` 의존성 캐시다. 실행 파일 복사본은 실행마다 분리하고, 증거도 매번 새 디렉터리에 저장한다. `CHROME_EXE`로 이미 설치된 브라우저 경로를 지정할 수 있다. 의존성이 없다는 이유로 설정/브라우저를 무단 교체하지 말고 러너가 표시한 준비 절차를 따른다. 자동검사는 headless, 수동 검수는 사용 가능한 내부 브라우저가 기본이다.

기존 시나리오에는8000 외8874·8767 고정 주소와 `BASE_URL` 환경변수를 쓰는 코드도 남아 있다. 목록의 `legacy URL: inspect source`는 **주소 미확인**이며8000 보장이 아니다. 비기본 `QA_BASE_URL`을 지원하지 않는 테스트는 러너가 거부한다. 시작/종료 부분을 공통 하네스로 이전하고 `lib/runner-utils.mjs`의 `BASE_URL_SCENARIOS`에 등록하거나, 실제 시나리오 URL과 서버 소유자·검증 대상을 확인한다. 옛 코드에 새 환경변수만 주면 적용됐다고 가정하지 않는다. `--all`은 명시적으로 전체 검사가 필요한 경우만 사용한다.

`QA_TIMEOUT_MS`는 시나리오별 제한시간(기본300000ms, 최대3600000ms)이다. 제한시간 초과는 정상 실패로 남기며, 임계시간을 늘려 실제 실패를 가리지 않는다.

## 전투별 시나리오 작성

실제 이전 예제는 [battle_lose](../../tests/playtest/battle_lose.mjs)와 [battle_bgm](../../tests/playtest/battle_bgm.mjs)다. 코드를 통째로 복제하기보다 다른 규칙만 추가한다.

| 공통 하네스가 맡는 것 | 시나리오가 맡는 것 |
| --- | --- |
| 브라우저/page 생성과 종료, 페이지 오류, 키 입력, 제한시간 대기, 스크린샷, 결과 파일 | QA 지점과 진입 조건, 메뉴/턴/기믹 상태 관찰, 전투별 독립 기대값 |
| 이름/설명이 있는 fixture 기록 | 왜 어떤 HP/턴/좌표/flag를 강제로 준비했는지, 자연 진행과 무엇이 다른지 |
| 전체 로그 보관, 짧은 실패 요약, 실행별 경로 | 준비→실제 키→타격/판정→턴/필드 복귀 assertions |

`runScenario(options, async context => { ... })` 안에서 `open`으로 QA 지점에 들어가고 `fixture`로 강제 준비를 기록한다. 이후 플레이어 행동은 `press`나 `page.keyboard`로 수행한다. 공통 `check`·`until`·`shot`의 정확한 인자 순서는 하네스와 두 실제 예제를 따른다. timeout을 무시하고 진행하거나 `state='win'`을 넣은 것을 정상 클리어 검사라고 보고하지 않는다.

예: 파크는9명중 충전/본체 공격 기회/재판 정답·오답, 영클은 특별 패턴 선택/전환/복귀만 각 시나리오에 둔다. HP·메뉴·전투 종료 검사는 재사용하되 패턴별 종료 분기를 생략하지 않는다. 아직 이전하지 않은 시나리오도 기존 assertions를 보존하며 단계적으로 이전한다.

## 결과는 요약부터 읽는다

러너가 출력한 실행 디렉터리의 `summary.json`을 먼저 읽는다. 테스트별 `output.log`는 전체 출력을 보관하고, 이전된 시나리오의 `result.json`은 검사/fixture/페이지 오류를 제공한다. 실패한 항목 주변 로그와 해당 캡처만 연다. 성공 로그 전체와 모든 이미지를 대화에 반복 첨부하지 않는다.

- 프로세스 비정상 종료는 `fails=0` 문자열이 있어도 실패다. 결과 마커 누락도 실패다.
- 이전하지 않은 시나리오의 fixture 기록이 없으면 ‘주입 없음’이 아니라 **미기록**이다. 실제 본문을 확인한다.
- 자동 PASS는 상태/입력/파일 검사 범위다. 캡처는 직접 열어 잘림·겹침·가림·간격·떠 있음을 본다. 연출의 자연스러움·실제 음색·사람 난이도는 별도 관찰한다.
- 오디오 엘리먼트 재생/시간/볼륨 검사는 사람이 들었다는 뜻이 아니다. 프레임 가속은 실시간 오디오 동기 증거로 쓰지 않는다.
- 재실행은 새 수정·실패 원인·누락된 관찰이 있을 때만 한다. 정확한 토큰 절감률은 측정 전 약속하지 않는다.

최종 기록은 실행 소스/URL, 선택한 시나리오, 주입 내역, 자동 결과, 직접 관찰, 미실행 영역, 증거 경로를 남긴다. 다른 모델/도구로 실행하지 않았다면 모든 에이전트에서 실행 검증됐다고 쓰지 않는다.
