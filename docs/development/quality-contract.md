# 섭타룬 개발 판단 기준

2026-09-14 사용자 요청으로 정리한 모델 공통 원본이다. 모델의 성능을 동일하게 만든다는 보장이 아니라, 다른 모델도 같은 근거를 읽고 같은 실패를 검출하기 위한 작업 계약이다. Claude와 Codex는 이 파일과 작업별 스킬을 공유한다.

## 시작과 복구

1. 이번 요청을 **플레이어가 보게 될 변화**로 한 문장 적는다. 원문 대사·지정 자산·입력·시점·완료 조건을 추출한다. 추가 피드백은 기존 요청에 합치고, 충돌하는 부분만 최신 지시로 갱신한다.
2. 현재 cwd/브랜치/미커밋 변경, `docs/STATE.md`의 관련 최신 항목, 실제 실행 파일과 서버가 서빙하는 경로를 대조한다. 이전 BUILD의 수치와 “미구현” 설명을 현재 사실로 복사하지 않는다.
3. 아래 라우팅에서 해당 스킬과 연결된 사례를 읽는다. 사용자 요구 → 현재 구현 → 관찰된 차이를 확인하면 수정에 들어간다. 맥락이 없다는 이유로 이미 완성된 모션을 다시 만들지 않는다.
4. 중단 가능성이 있는 작업은 `.omc/handoffs/<작업명>.md`에 요청 원문/최신 교정, 남은 요구, 작업 경로·브랜치·서버, 변경 파일, 확인한 SHA와 증거, 다음 행동을 저장한다. 복구 뒤 파일의 현재 내용과 다시 대조한다. 오래된 PASS는 변경 후의 증거가 아니다.

## 판단의 우선순위

- 최신 사용자 확정 → 현재 적용되는 프로젝트 계약 → 현재 코드/실제 화면 → 과거 회고·예시 순으로 판단한다. 코드가 사용자 요구와 다르면 요구를 코드에 맞춰 낮추지 않는다.
- **공통 원칙**은 입력/판정의 정직함, 연출의 인과·연속성, 기존 자산 정체성, 읽고 대응할 수 있는 난도, 실제 플레이 검증이다.
- **장면별 결정**은 색·조명 모양·숫자·속도·대사·음악 큐다. 마이야르 일출 시간이나 낙석의 평행광을 다른 무대에 그대로 강제하지 않는다. 특히 편집노조의 노란빛 제거/직사각형 교정은 중간 해석이며 최신 노란 부드러운 빛 요청이 우선한다.
- **아이디어**는 제안 상태로 표시한다. “향후 리듬/FPS도 가능”은 지금 그 모드를 만들거나 이후 전투를 자동 추가하라는 지시가 아니다. 사용자가 기획·구현을 맡겼다면 현재 범위의 구체적 선택은 근거를 적고 진행한다.

## 구현과 전달

현재 게임은 Canvas/JavaScript 엔진이다. 기존 엔티티·노드·레지스트리·모드 계약을 먼저 찾고, 필요한 차이를 가장 작은 소유 모듈에 넣는다. 표현할 수 없는 요구가 확인됐을 때만 공통 계약을 확장한다. 미정 미래 기능을 위해 범용 프레임워크나 별도 상태 기계를 선행 제작하지 않는다.

승인된 구현·수정·문서화 요청은 파일마다 재승인을 받지 않고 실행한다. 이미 확정된 메인 반영 지침은 `docs/STATE.md`의 “메인 반영·전투 확장 방향”을 따른다. 읽기·아이디어만 요청한 작업을 구현/배포로 확대하지 않는다. 새 사용자 결정이 없으면 결과가 달라질 정도의 불확실성만 질문한다. 옛 협업 템플릿의 무조건적인 질문/초안 승인 절차는 이 프로젝트의 실행 권한을 덮어쓰지 않는다.

완료는 요구별 관찰 증거로 판단한다. 테스트 개수, 리뷰 PASS, 이미지 존재, `hidden=false`, 상태값 변화만으로 화면·게임성까지 승인했다고 말하지 않는다. 확인한 실행 환경, 로컬/메인/원격/배포 여부와 미확인 범위를 구분한다.
