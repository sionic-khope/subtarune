# 섭타룬 기획과 기믹

[공통 판단 기준](../../../docs/development/quality-contract.md)을 읽고, 전투는 [전투 판단](../../../docs/development/combat-design.md), 지역/퍼즐은 [맵 판단](../../../docs/development/map-design.md)을 읽는다.

## 순서

1. 요청 범위를 아이디어만/구체 기획/구현으로 구별한다. 현재 캐릭터·구간·앞뒤 사건·플레이어가 이미 배운 규칙·지정 대사/자산을 확인한다. 이미 결정된 내용을 다시 선택지로 돌리지 않는다.
2. 열린 기획 문제라면 서로 다른 **플레이어 행동**을 요구하는 후보 2~3개를 낸다. 각 후보에 캐릭터 소재, 입력, 눈으로 읽을 단서, 성공/실패 결과, 이전 기믹과의 차이, 필요한 자산, 구현 위치, 가장 큰 위험을 붙인다. 단순 수치/색 변형은 별개 후보가 아니다. 사용자가 구체안을 정했다면 후보 단계는 생략한다.
3. 새로움·읽힘·흐름·개발 범위를 비교해 추천한다. 이 게임은 스토리 어드벤처이므로 긴 반복/노가다보다 사건과 놀이가 이어지는지를 우선한다. 유머는 반복 말투를 바꾸는 데 그치지 않고 행동·소품·카메라·타이밍 중 하나를 바꾼다.
4. 선택되거나 기획을 위임받은 안은 **학습 → 응용 → 결합 → 여유/결과**로 전개한다. 각 단계의 입력, 제한 시간(필요한 경우), 결과, 회복/재시도, 다음 구간 연결을 적는다. 모든 아이디어에 네 단계를 억지로 늘리지 말고 짧은 이벤트는 한 번의 인과로 끝낸다.
5. 기존 엔티티/패턴/모드/노드와 대조해 데이터 변화인지 새 계약인지 정한다. 여러 곳에서 공유하는 입력·HP·저장·승패 규칙은 원본 모듈에 남긴다. 새 기능을 실제 요구 없이 먼저 등록하지 않는다.
6. 구현 요청이면 해당 map/enemy/cutscene 스킬로 이어서 완성한다. 제안만 요청이면 구체적인 제안과 검증 방법을 전달한다. 미구현 기믹은 명확히 제안으로 남긴다.

## 기획 카드

설계 문서에는 다음을 실제 내용으로 채운다: 요청/확정·제안 구분, 플레이어 행동, 관찰 가능한 단서, 시간/공간 규칙, 성공/실패/재시도, 기존과 다른 판단, 필요한 자산과 담당, 구현 소유 파일, 조절 변수의 효과, 완료를 판정할 플레이 시나리오.

예를 들어 ‘편집자 보스’가 요청되면 컷 편집·순서 맞추기·음악 타이밍을 소재로 검토할 수 있다. 이는 **후보**이지 현재 편집노조 컷신 뒤에 전투를 추가하는 허가가 아니다. 리듬·춤·조준은 전투 attack/enemy 모드로 연결할 수 있지만 현재 기본 공격의 무조건적인 대체 규격도 아니다.

## 통과 기준

다른 구현자가 카드만 보고 입력·피드백·결과·초기화·연동 위치를 정할 수 있어야 한다. “더 재밌게/역동적으로/화려하게”만 남거나 제안이 확정 스토리에 섞이면 미완료다. 숫자는 현 구간 진행 상태와 실제 코드 근거를 명시하며, 검증 전 체감 난도를 확정하지 않는다.
