# 섭타룬 완료 검수

[공통 판단 기준](../../../docs/development/quality-contract.md)과 변경 분야의 기준을 읽는다. 검수자는 작성자의 설명을 결론으로 받지 않고 사용자 원문과 변경 결과를 대조한다.

게임 QA 실행·시나리오 추가는 [재사용 QA 가이드](../../../docs/development/reusable-qa.md)를 먼저 읽는다. 기존 러너와 공통 하네스를 재사용하고 전투별 조건/기대값만 확장한다. 요약→실패 로그→관련 캡처 순서로 읽어 불필요한 전체 출력·재실행을 줄인다.

1. **대상 고정:** 현재 브랜치/SHA, 미커밋 차이, 서버 경로/BUILD, 사용자 최신 요구를 확인한다. 스크린샷과 로그는 이번 실행의 새 경로에 저장한다. 변경 전 이미지나 다른 worktree의 화면은 현재 증거가 아니다.
2. **요구별 판정:** 각 요구에 실제 관찰과 실패 조건을 정한다. 예: ‘원래 있던 관중’은 소개 전부터 존재·보이고 줌아웃만 바뀌어야 한다. ‘어려운 패턴’은 피해 숫자가 아니라 회피 판단이 달라져야 한다. 요구 자체를 구현값에 맞춰 재작성하지 않는다.
3. **범위와 자동검사:** 게임 동작·레이아웃 변경은 [회귀 검사 선택표](../../../docs/development/regression-checks.md)를 읽고 변경 기능 → 진입 → 복귀 → 공통 소비자를 연결한다. 적용/제외 이유를 먼저 기록한 뒤 관련 검사와 커밋 전 `tools/dev/check.sh` 전체 검사를 실행한다. 테스트 기대값은 사용자 계약과 독립된 계산/관찰에서 정한다. 실패 경로를 실행하지 않는 stub, 무의미한 assertion, 실패를 숨기는 삭제/skip/only는 완료 근거가 아니다.
4. **실제 표면:** 실제 방향키/C/X로 해당 흐름을 실행한다. 맵은 접근 끝·출구·귀환, 컷신은 변경 직전/중간/다음 대사/조작 복귀, 전투는 예고/타격/대응/턴 복귀, 메뉴는 마지막 항목/취소/연타를 분야에 맞게 확인한다. 소리 변경은 실제 재생도 확인하고, 메타데이터만 확인했다면 청취로 표현하지 않는다.
5. **한계 구분:** QA 지점/fixture는 시작 상태 준비에 쓸 수 있다. HP/위치/flag를 강제로 바꾼 뒤의 결과로 자연 공략·정상 진행 완주를 주장하지 않는다. 화면 수치 통과와 미적 판단, 자동 회피와 사람의 난도 평가는 따로 기록한다.
6. **종료:** 장면을 끝내거나 취소한 뒤 영향받은 카메라/음악/파티/입력/저장을 확인한다. 지속 객체는 남고 임시 객체는 정리되어야 한다. 문제가 발견되면 원인에 맞는 부분만 고친 뒤 바뀐 흐름을 재검증한다. 새로운 변경/실패가 없으면 같은 검사를 반복하지 않는다.

## 최소 증거 기록

게임 QA 기록은 [증거 양식](../../../docs/development/regression-checks.md#증거-양식)을 사용한다. 자산만 전달할 때는 원본 디코드·PNG CRC/치수·프레임·실제 보이는 결과와 전달 계약을 확인한다. 파일 크기나 썸네일 표시만으로 원본 무결성을 통과시키지 않는다. 90k 같은 전송 청크 크기는 해당 도구에 필요할 때의 전송 설정이며 모든 검사의 합격 기준이 아니다. 최종 답변은 변경 결과·핵심 검증·원격/배포 상태를 짧게 전달한다. PASS는 관찰 범위에만 유효하며 사용자의 만족을 대신하지 않는다.

지침/스킬 변경은 [사례 과제](../../../docs/development/casebook.md)의 관련 요청을 다른 읽기 전용 에이전트에게 준다. 기대 답안을 미리 주지 않고, 읽은 경로·판단·구체 작업안을 받는다. 잘못된 승인 루프/과거 수치/무단 게임 변경/가짜 완료가 나오면 그 판단을 유도한 문구와 라우팅만 수정한다. 다른 실제 모델 실행을 하지 않았다면 모델 간 동등 성능을 검증했다고 보고하지 않는다.

문서만 바뀐 작업은 링크·현재 코드와의 일치·독립 사례 판단을 검증한다. 회귀 규칙을 준비했다는 이유로 전체 게임 플레이나 새 기능 수정을 시작하지 않는다. 결과에는 ‘지침 검증’과 ‘런타임 QA 미실행’을 구분한다.
